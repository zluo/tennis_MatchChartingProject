# Repository Guidelines

## Project Structure & Data Organization

This repository distributes Match Charting Project tennis data, rather than an application. Files live in the repository root:

- `charting-{m,w}-matches.csv`: match metadata, including players, tournament, date, and surface.
- `charting-{m,w}-points-{to-2009,2010s,2020s}.csv`: point-by-point records, partitioned by gender and era.
- `charting-{m,w}-stats-*.csv`: aggregate statistics, such as `Overview` and `KeyPointsServe`. Most values are integer totals, not percentages.
- `MatchChart 0.3.2.xlsm`: contributor workbook; its `Instructions` tab explains charting notation.
- `README.md` and `data_dictionary.txt`: project background and field documentation.

There are no application source, test, or asset directories.

## Development & Validation Commands

No build system, package installation, development server, or automated test suite is configured. Use lightweight checks when editing data:

- `head -n 3 charting-w-stats-KeyPointsServe.csv` — inspect the header and representative rows.
- `git diff --stat` — confirm the scope of changed files.
- `git diff --check` — detect whitespace errors in the patch.
- `git diff -- charting-w-matches.csv` — review individual record changes.

For programmatic validation, use a CSV-aware reader such as Python's standard-library `csv` module; splitting lines on commas can misread quoted fields.

## Data Style & Naming Conventions

Preserve existing filenames, column order, header spelling, charting notation, and record ordering. Keep dates in the existing `YYYYMMDD` format and retain established `match_id` values across related files. Avoid whole-file rewrites or incidental line-ending changes in these large datasets; `.gitattributes` enables automatic text normalization.

Only `1st`, `2nd`, and `Notes` in point files contain user-submitted data; other point columns are generated by the workbook. Account for derived fields when correcting records.

## Testing Guidelines

No testing framework or coverage target is defined. For data changes, verify row widths against headers, confirm affected match IDs exist in metadata, and check related point and aggregate records for consistency. Describe the checks performed in the pull request.

## Commit & Pull Request Guidelines

Recent data-release commits use short messages such as `thru 18 sep 2026`. Follow that pattern for dated dataset updates; use concise, descriptive messages for corrections or documentation.

Pull requests should identify affected files and matches, explain the correction or data source, summarize validation, and link relevant issues when available.
